## R14a - one merged timeline for the order group

`/clubs/objednavky/:orderId/historie` now reads the order, its addenda and the order an addendum belongs to (`GET /api/v1/club-orders/{id}` for each; no
new endpoint) and shows ONE list, newest first.

| Part | What it does |
|---|---|
| `pages/clubs/orders/historyTimeline.ts` (pure, tested) | `classifyHistoryText` gives every line its kinds from the wording the backend writes; `buildTimeline` merges the lines of the group; `filterTimeline`, `kindCounts`, `groupOrderIds` |
| Kinds (chips) | Stav (čeká na formulář, potvrzeno, zrušeno, dokončeno), Dodatky (created, cancelled, merged), Hráči (seats changed, players turned out, a player cancelled), Termíny (windows added / removed / moved, time given back, offered days), Zprávy klubu, Faktury, Ostatní. A line can have several kinds ("Objednávka upravena: místa (...); časové bloky (...)" is Hráči AND Termíny) and is found under each chip |
| Entry | kind label (no icon), time in Prague, who, the order it is on when the group has addenda ("Dodatek KO-..." / "Objednávka KO-..."), "Vidí klub" tag, the text, and a link: an addendum line -> that order's panel, an invoice line -> `/billing` (only offered to a person with `billing.manage`) |
| Views | "Vše" and "Co vidí klub" as before; the chips work inside both, with counts for the view that is on |
| Dedupe | the addendum's own "Dodatek k objednávce ..." and "Objednávka zrušena spolu s hlavní objednávkou ..." lines are left out (the root says the same) so a creation is one entry, not two |
| The desk's own words | text after "Zpráva ordinace:" / "Důvod:" never decides the kind (a reason that says "dodatek" is not an addendum event) |
| Failures | an addendum that cannot be read: the rest is shown with "Historii jednoho dodatku se nepodařilo načíst" and a retry |
| Order panel | unchanged by this stage: it already had only the status chip and the "Historie" button |

### What the order history already recorded, and what was missing

Measured in `ClubOrderService*`, `ClubOrderInvoiceService`, `ClubOrderNotices`, `ClubOrderReleaseService`:

| Event | Recorded before | Now |
|---|---|---|
| order created / form sent / confirmed / completed | yes | yes |
| cancellation | yes, but the desk line had no reason (only the club-facing line did) | `Objednávka zrušena. Důvod: <zpráva>` |
| addendum created | yes, on the root and on the addendum | same, shown once |
| addendum cancelled together with its root | yes | same |
| addendum cancelled ON ITS OWN | only on the addendum, the root's story had a hole | NEW: `Dodatek KO-... zrušen. Důvod: ...` on the root |
| seats (players) changed, players turned out, a player cancelled | yes | yes |
| windows added / removed / moved | yes (`časové bloky (n přidáno, n zrušeno, n upraveno)`, `Termín ... byl zrušen`, `Ordinace změnila termíny`) | yes |
| messages to the club | yes (`Zpráva ordinace: ...`) | yes |
| invoices | yes (společná / dodatečná faktura) | yes |
| a player JOINING through the club's link | **no** - it is an appointment, not an order-history line | still not recorded; the page does not claim it (see open risks) |

No migration: the history is the existing append-only `ClubOrderHistoryEntry` text lines. The frontend therefore classifies by wording, pinned in
`historyTimeline.test.ts` against the exact strings the backend writes; a line it does not know is "Ostatní", never dropped.

### Backend

* Permission `exports.download` (`ApplicationPermissions.ExportsDownload`): in `All`, so the Owner has it; in the Administrator's role defaults; NOT in Staff.
  Role defaults, not rows: nobody has to be seeded and an Owner/Administrator cannot lose it by accident (an Administrator can be revoked on purpose through
  the existing permission overrides; the Owner cannot, as for every permission).
* `ExportDownloadAttribute` (authorization filter + result filter): 403 `ApiProblemResponse` code **`export.forbidden`** before model binding, an
  `access.denied` audit row for the refusal, and after a file response the audit row **`export.downloaded`** (entity `ExportDownload`, keys `kind`, `count`,
  `format`; who, when and the IP are the audit row's own). No name, id, file name or patient identifier. Routes: see the contract (accounting, audit CSV,
  invoice PDF, diagnostic PDF, certificate PDF, documents `?download=true`, patient export, backup, recovery sheet).
* `GET /api/v1/exports/policy`, `POST /api/v1/exports/authorize` (client-built files: statistics, player lists).
* CSV: the audit export and the accounting CSV are now UTF-8 with a byte-order mark; amounts stay to the haléř (`0.00`), the browser-built CSVs write the
  number exactly as JavaScript holds it (no rounding anywhere in the helper).
* No migration, no schema change.

### What PDF quality is really reached

QuestPDF 2024.12.1 draws all PDFs through five renderers (the invoice, two for the medical-fitness certificate, two for the diagnostic reports). `PdfQuality.Best` (one in `Infrastructure.Billing`,
one in `Reporting.Rendering.Pdf`) sets `PdfA = true` (the library's PDF/A-3b: XMP metadata with `pdfaid`, a document id, an sRGB output intent),
`CompressDocument = true`, `ImageCompressionQuality = Best`, `ImageRasterDpi = 600`. Text and drawing stay vector with the Lato fonts embedded (checked in a
real invoice PDF from the running API: `pdfaid:part`, `/OutputIntents`, `/FontFile` present, 77 KB). The only raster in the invoice is the QR payment code, kept
as a PNG. **Honest limit:** the library emits the PDF/A structures but does not validate conformance, and PDF/A-3b rather than 2b is what it produces; nothing in
this repository runs veraPDF, so "PDF/A-conformant" is not claimed, "PDF/A-3b structures, embedded fonts, vector" is. Images and logos are not downscaled (the
frontend saves the server's bytes untouched; the PDFs contain no uploaded images today).

## Open risks

* The kinds are read from the wording of the history lines. A reworded backend line falls into "Ostatní" (still shown); the tests pin today's wording. A `kind`
  column on `ClubOrderHistoryEntry` would be sturdier but needs a migration (not done: "additive on the existing pattern").
* A player joining through the club's link is an appointment and is not an order-history event; the group timeline cannot show it. Needs a decision whether
  `PartnerOrderService` should write a line (it is the busiest write path of the club flow).
* A staff member without the permission who already has a patient document open can still use the browser's own "save as" on the viewer; the server gates
  only `?download=true` and the app has no such button.
* An older backend has no policy route: every button stays enabled there and a file the browser builds is saved without an audit row (nothing exists to write it).
* The shared `core.hooksPath` is stale; commits used `-c core.hooksPath=.githooks`, the ownership hook did not block anything.
